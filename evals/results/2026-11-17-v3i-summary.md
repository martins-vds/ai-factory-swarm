# Phase 3e: rules checked (2026-11-17, v3i)

These runs measure harness #192 and eval #1061. A Verifier return now lists `rules` covering every capability
the plan gives the ticket. Each rule names the use-case test that shows whether the rule is enforced; a
capability with no rule goes under `no_rules`. There were three runs of the seven Verifier cases, compared with
v3h by majority (`afs-eval compare`).

| Case | v3h | v3i r1 / r2 / r3 | v3i majority |
|---|---|---|---|
| BK-05E, BK-05G, LL-02, LL-03, LL-04 (defect) | 3/3 pass each | P P P each | pass |
| LL-05 (clean) | 3/3 pass | *invalid* / P / running | see below |
| BK-05F (defect) | 0/3 fail | F F running | **fail** (r3 can't change it) |

**The five deterministic cases held at 3/3 each.** Sessions ran longer: median requests and minutes both rose
23%. BK-05F's sessions doubled in length.

## BK-05F: the rule list didn't help, and why

Every Verifier listed rules for every BK-05F capability; the finish check made sure of that. But each chose
rules the use case already enforces:
- "candidates arriving after the deadline are not offered";
- "assignment to an unknown tracking ID is refused".

None listed the rule that is misplaced: an itinerary must satisfy the route specification, and only the view
checks that.

That rule appears nowhere a tool can read:
- the plan's BK-05F scope doesn't name it;
- the `booking.routing-assign` ledger entry doesn't name it.

So the coverage check can only make sure that some rule is listed for each capability, not that the right
rule is. A Verifier finds this defect only by reading the view and noticing the guard, which happened in one
run of v3g and in none since.

## LL-05: a case-definition error (mine)

LL-05's r1 Verifier returned `changes-required`: "the LL-05 diff deletes prior-slice acceptance and audit
evidence". It was right about the diff it was given, but the diff was wrong. I gave the case base `2e4b196`,
which is not an ancestor of the work `007072d`; the work branched from `7d4b249`. So the diff showed
later-added `main` files as "deleted". The case now has the right base (`7d4b249`, the same as the
`synthetic-ll-05` Migrator case). r1 doesn't count, and LL-05 needs a re-run to be judged. v3h's three passes
had the same wrong base; no Verifier flagged it then.

## Decision

The done condition isn't met: BK-05F fails, with no ruling, and LL-05 must be re-run. ADR-0043 stays
**Proposed**. Two ways to close phase 3e:

1. **Give rules a source upstream.** The Characterizer or Migrator would record each capability's business rules
   in its ledger entry (`rules:`). The Verifier's `rules` must then cover the ledger's. This puts the
   eligibility rule where a check can see it.
   - It changes roles that have no eval case yet (the Characterizer; `afs-eval coverage`), so it can't be
     measured until one exists.
   - It's a larger piece of work, closer to phase 3d.
2. **Accept ADR-0043 now with BK-05F as a recorded limit.** Rule-placement defects outside every spec are found
   by review only sometimes, against 1 of 6 cases before phase 3e. Move on to phase 4a, and re-run LL-05 with
   the corrected base as part of the next measurement.

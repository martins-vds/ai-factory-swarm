# Phase 5 re-run: the shortened prompts, measured (2026-11-21)

The phase 5 eval (2026-11-19) ran the prompts of harness `ca620b9`: the eval repo's `main` hadn't been
updated with the harness under test (ADR-0058). This re-run uses the agents that ship: harness `764f75b`
and later, with `main` synced (eval #1944). It is pinned to the baseline's model, `gpt-6-luna` (ADR-0060).
The set is the must-pass cases (except three disabled verify cases), the three slice acceptances and the
bootstrap case.

## Result
**No flips: ADR-0053's shorter prompts hold.** No case that passed by majority in the phase-1 baseline fails
by majority now. By majority, 18 of 22 cases pass; the baseline passes 4 of the 16 cases both have. Eight
cases go from fail to pass. Full table: `2026-11-21-p5r-compare.md`.

Runs counted: r1's `gpt-6-luna` rows, r2, r3, and x1/x2 (DM-05D, DM-05F and BK-05G again after #223).
These are excluded:
- **r1's 8 `mai-code-2-flash` rows.** r1 ran before the model was pinned; the `.luna.json` copies mark
  those rows not-dispatched.
- **Setup failures:**
  - r1's bootstrap case (the `source.lock` guard, fixed in #220 and eval #2060);
  - DM-05D and DM-05F in r2, r3, x1 and x2, whose data-snapshot fetch was rate-limited (#223).

## What doesn't pass
- **pilot-bk-05g (1 of 5).** The live continuation ticket says "Change that template only to open the
  dialogs". The first session had built no dialogs. Since r2, every run has read that sentence as the whole
  scope: it found no dialog views to open and handed off, saying a template alone can't make working
  dialogs. The phase 5 runs (old prompts) and r1 read it as an added file and built the dialogs too.
  - Both readings are defensible. The ticket's wording is ambiguous, not the harness.
  - Whether the shorter prompts or chance made the stricter reading common isn't settled by 5 runs.
  - The fix is the case's (and a live dispatcher's) wording, not a rule.
- **pilot-dm-05d (0 of 1 valid run).** r1's only valid run ended with `afs-mutation` crashing on
  `exporter.py` twice; the error wasn't committed (#222 now commits it). Every later run lost its data
  snapshot to the API rate limit, even with #223's retries.
  - The eval repo's workflows share one `GITHUB_TOKEN` budget per hour, and about 30 concurrent sessions
    plus their CI use it up.
  - DM cases need a quiet window. **This case is unmeasured, not failing.**
- **synthetic-ll-01 and synthetic-ll-03 (1 of 2 each, a tie).** Both r3 PRs failed CI's browser tests
  (`test_loan_catalog_renders_in_browser`, `test_htmx_payment_failure_is_rendered_in_the_fee_page`). The
  same tests passed in the other runs and in phase 5. I haven't yet looked at whether the target's tests are
  flaky under load or the agents' code is at fault.

## Other things this run found
- **The eval repo served stale agents** from 2026-11-18. ADR-0058 makes `prepare` refuse that.
- **Copilot mixed two models from 2026-11-20.** ADR-0060 pins the model and records it per session.
- **Environment failures that read as agent failures:**
  - the bootstrap setup step without a `source.lock` (#220);
  - the rate-limited snapshot fetch (#223);
  - a live branch name in the issue (#223's eval note).

and are compared with the b3c regrade ([2026-11-17-b3c-verifier-regrade.md](2026-11-17-b3c-verifier-regrade.md))

**By majority: 3 of 6, up from 1 of 6.** The rule `compare` applies reports one flip the wrong way: LL-04.

## What changed, by kind

- **Layering defects a tool can find are now caught every time.** BK-05E (the view calls the repository) and
  LL-02 (the use cases import the clock and the ORM) pass in every run. Both fail the idiom gate's layering
  check, and each Verifier reported the failure as a major finding citing the run.
- **No serious finding on clean work came without evidence.** BK-05G passes in every run, against 1 of 3
  before. Its b3c false positive, "the URLconf omits the booking routes", didn't return.
- **The finish check enforced the rules.** In BK-05E r2 it blocked the Verifier twice on `validate.py` errors
  in its return before allowing it. Every other block was for a return not yet written.
- **No case ended `verifier-blocked`.** BK-05F r1 returned `blocked` on an interrupted mutation run, with the
  gate named. That case allows `blocked`, so it was graded on its findings.

## The two defect cases that still fail

- **LL-03 (htmx 2 doesn't swap 4xx/5xx).** Found in r2, with a failing test as evidence. In r1 and r3 the
  Verifier passed the work. A tool can't see this defect; it needs a review that exercises the htmx error path.
- **BK-05F.**
  - **The eligibility check sits in the view, not the use case.** No run found it.
  - **The `Http404` in the use case.** r2 and r3 saw it but reported it as *minor*: the layering gate lists it
    as known debt from BK-05C, which this ticket depends on. r1 blocked on an interrupted mutation run, with no
    findings. The Verifier prompt says to "report
    it when the ticket's code relies on it", but it doesn't say how severe it is.

## LL-04: the clean case that now fails, on a real defect

In every run, the Verifier wrote a failing test showing the same major finding: the About page's stylesheet
`/static/css/tailwind.css` returns 404. This is a real defect, and it is still on synthetic `main`:
- `static/css/tailwind.css` is committed at the repo root;
- `config/settings.py` sets only `STATIC_URL`, with no `STATICFILES_DIRS`, so Django never serves the file;
- `templates/base.html` links it, so every page renders unstyled.

LL-01 introduced the defect; LL-04's About page inherits it. The b3c Verifiers missed it.

So the flip is the Verifier getting better, not worse, but the case expects `pass`. Both this case and BK-05F
turn on one question for the operator: **how severe is a defect from an earlier ticket that this ticket's
work depends on?**

| Ruling | LL-04 | BK-05F | Majority |

| Always major | becomes a defect case: 3/3 pass | the prompt makes known debt major; re-run | 4 of 6, maybe 5 |
| Never major (report it apart) | stays clean; the prompt makes inherited defects minor; re-run | the Http404 leaves the expectation | depends on the re-run |

## Decision

The phase 3e done condition isn't met yet:
- BK-05F and LL-03 fail by majority, and neither carries a ruling that explains why;
- LL-04 needs the ruling above.

ADR-0043 stays **Proposed**. Its first two decisions (the layering gate; verdicts that follow evidence-backed
findings) did what they were meant to: 3 of 6 cases flipped to pass, and no clean case failed on an unproven
finding.
